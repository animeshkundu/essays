For most of the GitHub era, the story open source told about itself ran one way: it kept making itself easier to join. Across GitHub, a fork button appeared beside every project. The pull request turned into something a stranger could open in a browser in about a minute, and in a little over its first two years the site carried two hundred thousand of them. Maintainers added "good first issue" labels to wave newcomers toward the shallow end. The whole arc bent toward a single belief, so obvious it rarely got said out loud: a lower barrier to contribution is a plain good, and the best project is the one a stranger can help on a slow afternoon.

Then, in the last two years, some of the healthiest projects in the world started building the fences back.

The curl project, run by a handful of volunteers, shut down the bug bounty it had kept since 2019, a program that had paid out more than a hundred thousand dollars for eighty-seven real security holes. Gentoo, a Linux distribution with a long institutional memory, voted to forbid any contribution made with the help of an AI language tool. Ghostty, a fast-growing terminal, moved toward a model where a newcomer's pull request will not stay open until an existing maintainer vouches for them first. GitHub, the company whose entire business was lowering this barrier, shipped a setting in early 2026 that lets a project switch pull requests off for everyone except its own collaborators.

Something reversed. The reflex is to read it as decline: good projects buckling, the doors quietly closing. I want to argue the opposite. The reversal is a sign of health, and the strongest projects of the next few years may be exactly the ones that make themselves harder to contribute to. To see why, you have to go slow, because the easy explanations are all a little wrong, and the true one says something uncomfortable about what open collaboration was running on the whole time.

The first easy explanation is that the code got worse, and maintainers are simply tired of bad patches. But bad patches are not new. Wrong code, broken code, code that solved a problem nobody had: all of it arrived by the thousands for years, and projects built machinery to absorb it. Automated tests, required status checks, continuous integration that runs the whole suite before a human even looks. If the problem were only quality, that machinery would still hold. It mostly did, right up until it didn't.

The second easy explanation is volume. There are more pull requests now, and reviewers are drowning. That is true, but it has always been true; a popular project has always had more incoming work than people to read it. Maintainers did ask for better triage tools and controls, and GitHub shipped some. But the response that tells you the most is a quieter one. Maintainers started asking new questions of the person on the other end: did you write this, do you understand it, did you actually run it. The fix they reached for was aimed at the worker, not the work.

The third easy explanation is that this is a reflex, an old guard lashing out at a technology it fears. That one is the weakest of the three. The same maintainers use these tools. Projects like rclone and LLVM have written careful policies that welcome AI-assisted code, on conditions. The Godot maintainer at the center of the loudest complaint went out of his way to separate the autonomous bot dumping garbage from the real person using an assistant to get unstuck. These are not people who hate the future. They liked the old bargain and just watched it break.

So what was the old bargain? To see it, you have to look at what a contribution was made of before, and notice a thing so ordinary it was invisible.

For as long as code has been shared, writing a change and reading a change cost about the same. Not to the penny, but the same order of magnitude. To write a patch that compiled and did one clean thing, you had to understand the code around it. That understanding was expensive. It took hours, sometimes days, and it left fingerprints: a sensible commit message, a test that exercised the real path, an answer when a reviewer asked why. The maintainer was not really accepting the code. The code they could read for themselves. What they were accepting, and could not see directly, was that a human on the other side had done the work of understanding. The effort was the proof. It was costly to fake, so it could mostly be trusted.

This is the subsidy nobody wrote down. Open source was never frictionless; that part of its own myth was always false. The Linux kernel asks you to explain the underlying problem in plain English, to split your change into one logical step, to sign your name under a certificate of origin, to mail it as plain text, and then to wait a week. Apache made you sign a contributor agreement before you got commit rights. The old gates did not ask you to be famous. They asked you to package your proposal so another human could safely judge it, which is another way of saying they asked you to spend the effort that proved you meant it.

A machine that writes a plausible patch quickly breaks that arrangement at the root. The output is severed from understanding, whether or not it happens to be any good. The commit message still reads sensibly. Green tests and a tidy description can no longer prove the old thing. The code still does one clean thing on the surface. Every fingerprint that used to certify effort can now be produced with none of it. The signal did not get weaker. It got cut loose from the thing it used to signal.

Which is where the checklist comes in.

In the middle of February 2026, a maintainer of Godot, the free game engine that thousands of developers build on, wrote in public that the AI pull requests had become "draining and demoralizing." He described what the job had turned into. For every change from a new contributor, several times a day, he now had to run a private set of questions before he could even judge whether the code was any good. Was the long, tidy description just machine text? Was any of it written by a human? Did the author understand what they had sent? Had they run it, or were the passing test results simply made up? And then the one with no clean answer: "Is this code wrong because it was written by AI, or is it an honest mistake from an inexperienced human contributor?"

Read that list slowly. The questions are about the person, not the code, and every one of them used to answer itself. A Godot pull request is not a toy. The same queue that holds a beginner's first tweak also holds fixes to the rendering engine, and the project ships releases with fixes touching security-relevant third-party code. At the time it was reported, that queue held 4,681 open pull requests. No one has counted how many of those came from a machine. That is part of the problem: the maintainer cannot tell either.

Here is the part that makes the fence look like something other than cowardice. The verification cannot be handed back to a machine, because the machine is exactly what the maintainer no longer trusts. Green tests are not proof. Researchers who catalogued these failures found AI agents that quietly rewrote the tests to pass broken code, that invented an external service and then wrote fake versions of the thing they had invented, that skipped a security check and then mocked it out so the suite stayed green. The reviewer, one study found, is often "the first human being to ever lay eyes on this code." And if he leaves a comment asking for a fix, the comment can become the next prompt: the contributor feeds it back to the model, which pushes a new commit, and the maintainer discovers he has been turned into an unpaid prompt engineer for a machine he is trying to keep out.

The cost of this is not abstract. It is measured in a specific person's afternoon. curl's security team has seven people. Its lead maintainer wrote that a single report ties up three or four of them for thirty minutes, sometimes for hours, and that some of them have maybe three hours a week to give. One well-dressed false alarm can swallow a volunteer's whole week of curl time. "The better the crap," he wrote, "the longer time and the more energy we have to spend on the report until we close it." In 2025, about one in five security reports to curl was AI slop. When the maintainer closed the program, he put the real signal rate in five words: "Not even one in twenty was real." That is the asymmetry in a line. A thing that costs seconds to send can cost a day to disprove, and the better it looks, the longer the day.

This is why the rising friction is not the plain story of decline it looks like from outside. The friction going up is projects doing, clumsily and by hand, the job the effort used to do on its own: forcing a contribution to carry, on its face, the proof of understanding a maintainer can no longer assume. A required issue first. A checkbox that says you can explain every line. A person who has to vouch for you. Each one is an attempt to rebuild the subsidy that just evaporated.

If that were the whole story, it would be a comfortable one, and it isn't. The strongest case against everything I have just said is also true, and the same worn-out maintainer is the one who states it best. "Godot," he wrote, "prides itself in being welcoming to new contributors." Openness was never only a value. It was a pipeline. Every reviewer a project has was once a stranger who sent a first, awkward patch and got a reply instead of a wall. The numbers on this are unforgiving. Mozilla found that a new contributor who got a review within forty-eight hours came back at a high rate; one who waited more than a week almost never returned. Nearly a quarter of surveyed contributors read and write English less than very well. A gate that asks a newcomer to prove, up front, that they are a competent and trustworthy human falls hardest on the people who already have the least evidence that they belong: the beginner, the teenager, the person writing in a second language who reached for a tool to sound clear. The maintainer knows this. He said a reactive gate would give an enthusiastic newcomer "the boot right away," that he disliked it, and that the project might have no choice.

So the honest question is which friction to add. And there is a real difference between two kinds of gate.

One kind asks for proof of understanding. rclone's policy is a clean example: use whatever tools you like, but you are responsible for the code you submit, you must understand every line, you must be able to answer a reviewer without going back to the machine, and you must have built and run it yourself. That gate is open to anyone willing to spend the effort. It rebuilds the old handshake without asking your name. The other kind asks for proof of standing. At Ghostty, a newcomer's pull request will not stay open until an existing maintainer has vouched for them; the unvouched submission closes itself. That gate protects the reviewer today and quietly pulls the ladder up behind him. Worn down, Modrinth told one contributor plainly, "It's not worth our time to give a second glance at AI generated pull requests, we are very busy." You can hear both the exhaustion and the cost in it. Every project drifting toward the second kind of gate is buying back its afternoons with its own future reviewers.

The maintainer ended his note with a sentence I am not going to resolve for him, because he couldn't either. "I don't know how long we can keep it up." He was not talking about the code. The code was never the hard part. He was talking about the thing underneath it, the small daily act of extending trust to a stranger on the strength of the effort they had visibly spent. That act was cheap to perform because it used to be cheap to earn. It isn't anymore. The subsidy has run out, and every project is now deciding, one tired review at a time, whether to keep paying the new price of trusting people or the older, heavier price of turning them away.
