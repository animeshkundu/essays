At a quarter to ten on a July night, a man who has kept the same open-source project alive for almost nine years pulled up a chart of his own work. Out of curiosity, he wrote, to see if he could find a useful picture of what the new coding agents had done to his output.

The chart is a plain thing. GitHub draws it for any repository: green bars for the lines added each week, red bars for the lines deleted, stacked above and below a center line, one column per week. His ran from 2018 to now. For years the bars are short and uneven, activity coming in sporadic bursts. Then, at the far right, in 2026, the green climbs to a height nothing before it comes close to. In a single stretch, 37,022 lines added, with 9,528 taken away. A cliff. He noted that the last spike lined up with the tools he had been using, a short list of coding agents and frontier models from the past year, and published the chart.

Sit with the picture for a moment. Nine years of careful, uneven craft, and then a wall of new code taller than all of it, produced in weeks. If you run a team, or a company, or you are the person who has to keep this thing working, the honest question the chart raises is not how much did we ship. It is quieter than that. Who is going to own all of that green.

Here is a second number to set beside the first. A code-analytics firm spent this year measuring 623 million changes across three years of commits, from 2023 to 2026. Over that window, duplicated blocks of code rose 81 percent. The share of edits that moved existing code rather than adding new code, their closest proxy for cleanup and refactoring, fell from 13 percent to 3.8 percent. And the share of edits that touched any code more than a year old, the ordinary act of maintaining what already exists, fell from 1.7 percent to 0.46 percent. The firm that ran the numbers is cautious about blame, and so should we: this is a correlation across a noisy sample, not proof that one tool did it. Its point is not that the machines write bad code. The default way we work with them rewards a happy path, a passing test, and a closed ticket, and taxes everything else. More code, arriving faster, connected to less of what was already there, and touching the old code almost not at all.

So here is a claim most people building these tools would argue with: the best coding agent is not the one that writes the most usable code. It is the one that writes the least. The number we should grade an agent on is not accepted pull requests, or lines produced, or how fast it closes a ticket. It is how often it finds the code that already does the job, deletes a path we no longer need, and proves that the right amount of new code is none.

We have made the opposite mistake before, and we kept a good record of it. In early 1982, on the team building one of the first personal computers built around a graphical screen, managers asked engineers to turn in a form every Friday. One field wanted the number of lines of code you had written that week. One engineer had just rewritten the part of the system that draws and clips shapes on screen, using a simpler and more general method. It made the drawing routines almost six times faster. It also removed about 2,000 lines. Asked on the form how many lines he had written, he entered minus 2,000. After a couple of weeks, they stopped asking him to fill out the form.

The story is told as a joke about a clueless metric, and it is one. But the problem was not that lines are meaningless. The metric could only see the green. It had no column for the far more valuable thing the engineer had done, which was to make the program smaller, faster, and easier for the next person to hold in their head. Forty years later we have built agents that are extraordinarily good at filling in the lines-written column, and we are once again pretending that column is the score.

The agents lean this way for a simple reason, and it is not a flaw in the models. The pull comes from the shape of the work we hand them. When you assign a task to a coding agent today, it clones the repository, works in a fresh environment, and pushes its result to a draft pull request. The thing you get back, the thing you review, the thing your dashboards count, is a diff: a set of changed lines. Every metric around it counts changed lines too. Adoption, acceptance rate, lines added, pull requests opened, pull requests merged, time to merge. There is no field, anywhere on that instrument panel, for code the agent decided not to write.

The benchmarks work the same way. The standard test for these systems hands the model a real bug and a real codebase and asks it to produce a patch that makes the failing tests pass, then reports one headline number: the percentage of issues resolved. A patch that passes is a success. There is no way, inside that test, to earn credit for reading the code and reporting that the fix already exists three files over, or that a line of documentation would do, or that the cleanest resolution is to delete the feature that caused the bug. The only resolution the scoreboard can score is a patch. So a patch is what it pulls for.

You can watch this at the smallest possible scale. Earlier this year a crash in a popular code editor was hitting 827 people: a specific null value slipping past a specific guard. An agent found it and fixed it. The fix was one line, in one file: an added check. It was exactly right. And before it could go in, it sat with every automated check green and no unresolved comments, in a state the system marked plainly: blocked, awaiting required human review. Two maintainers read it and put their names to it before the one line could merge. The machine could write the line in a second. It could not be the one to own it. That small human act, saying yes, this line is ours now, is the part that did not get faster.

The code the agents leave behind also accumulates in a particular way. On one codebase this summer, a cleanup pass went looking for the AI-generated duplication scattered through the project, and found the same small helper functions pasted again and again: one routine for formatting a timestamp copied ten times, of which only a single copy carried a fix the other nine were missing, a small correction for how Safari and SQLite read the date format; a function for returning a JSON error defined 23 separate times; eleven hand-rolled versions of the same basic string encoder. Consolidating all of it into shared, tested versions was real and valuable work, and it removed more lines than it added. A review tool estimated a person would need about seventy-five minutes just to check the change, and the same tool still turned up two more duplicate copies the cleanup had missed. This is the maintenance bill for cheap generation, and someone has to read it one duplicate at a time.

The cost does not always land on the next programmer. On another project this spring, an AI pass through the documentation quietly stripped fifty-nine screenshots out of the installation pages, the exact pages the support team linked customers to when something broke. The words were still there. The pictures people actually needed were gone, and someone had to notice, dig up a pre-AI copy of the pages, and put them back. More content, less of what the reader came for.

Zoom out and the shape holds. In this year's large audit of commercial codebases, the average application carried 1,180 open-source components, up 30 percent in a single year, and nearly two-thirds of them were dependencies no developer had chosen directly. In the same audit, the mean codebase had grown to more than 84,000 files. Every one of those components and files is something someone now owns: has to patch, has to watch for the security hole, has to understand when it breaks in the middle of the night. In the codebases that reach an audit, software has quietly become mostly other people's code, held together by a thinning layer of your own. And the agents we score by lines added and pull requests merged are built to add to the pile, not to shrink it.

None of this means the right answer is always less, and that is the part the argument has to earn. A great deal of code exists only because generation finally got cheap enough to produce it: the test nobody had time to write, the internal tool that was never worth a sprint, the logging that made a mystery outage legible. If the real alternative was not elegant reuse but nothing at all, then the generated version is pure gain, and telling an agent to write less would be telling it to leave value on the floor.

Reuse is not free either, and anyone who has run production knows it. The standard advice against writing your own small function is that you can just pull in a package. Then one day the author of an eleven-line package that got fetched more than two million times a month took it down over a naming dispute, and installs broke across the internet for two and a half hours. A few years later a widely used stream library quietly took on a new dependency that turned out to be built to steal cryptocurrency, and it ran, in production, across millions of installs, before anyone noticed. A dependency is not free code. It is a decision to let a stranger own a piece of your program. Sometimes the smaller, safer thing really is to write the few lines yourself. The old proverb has it right: a little copying is better than a little dependency.

So the claim is not that agents should never write code. It is narrower and harder to wriggle out of: we are measuring the wrong thing. We reward the patch and ignore the judgment, and then we act surprised when we get more patches and less judgment.

What would it look like to measure the other thing. Not vaguely, but as something you could actually score. An agent working on an issue could be graded, first, on whether it found the maintained component that already solves the problem before it wrote anything. On whether it deleted a duplicate path instead of adding a parallel one. On whether it updated the old code rather than routing around it. On whether, faced with a possible dependency, it made the call in either direction with a clear accounting of the cost: the license, the maintenance history, what breaks if that package disappears. Rejecting a package because the local code is safer should count as much as adopting one. And on whether it can close a task with no new code at all: not by shrugging, but by naming the existing function that already covers the case, listing the paths it searched to be sure, and leaving a test that passes against the old code so a reviewer can rerun it. That last one is the hard one to build, because the difference between a real "this is already handled" and a lazy "I couldn't find anything" is exactly that evidence. A no with a citation, a search trail, and a green test is worth crediting. A no with none of that is just a refusal wearing a benchmark's clothes. Five things a reviewer could check, and not one of them shows up as a taller green bar. That is the point.

No such benchmark exists yet, and that is the argument's own limit. Every scoreboard we have counts patches, pull requests, lines, and merges; the non-creation score is, for now, a proposal, not a number you can look up. It is easy to say we should reward restraint and hard to build the instrument that does, because the whole difficulty is that the good outcome leaves no artifact. A closed issue with a comment that says the existing function already handles this looks, on every chart we draw, like nothing happened.

Which brings it back to the man and his chart. The easy reading of that cliff is a cautionary tale: a flood of machine-made code, debt dressed up as progress. But that is not quite what his record shows. The same tools that built the cliff also wrote the tests that guard it. One of them, asked to review the project's own interface for consistency before a long-awaited stable release, produced a careful audit. Weeks earlier, on the same family of projects, another was pointed at the security of a new feature and found a real way to steal data. The leverage and the liability came from the same tools.

So he is left where the chart found him: not with a mess to condemn, and not with a triumph to celebrate, but with 37,022 new lines that are now his to keep. The agents wrote them without a second thought. They will not be the ones, a year from now, reading the strange old line at two in the morning and trying to remember why it is there. That part still has an owner. The only real question the chart asks is whether we are building tools that help him carry the code, or tools that are very good at handing him more of it.
